# Contributing

Contributions are welcome from legal, compliance, security, risk, product and engineering practitioners.

## Contribution principles

1. Work from sources you are permitted to use.
2. Keep observed facts, normative conclusions and organisational policy separate.
3. Add an exact anchor for every normative rule.
4. State whether a source is binding law, guidance, a voluntary framework or an organisational policy.
5. Add positive, negative and unknown test cases for material rule changes.
6. Describe coverage and known gaps honestly.
7. Do not include confidential data, private doctrine or protected standards.
8. Write explanations that a non-technical professional can understand.

## Developer Certificate of Origin

The project uses the [Developer Certificate of Origin 1.1](DCO). Sign commits with:

```text
Signed-off-by: Your Name <your.email@example.com>
```

Use `git commit -s` to add the line automatically. By signing off, you certify that you have the right to submit the contribution under the applicable project licence.

## Rule-pack review

A public pack change should include:

- the authoritative source and relevant date;
- a plain-language explanation of the change;
- a machine-readable rule and stable identifier;
- tests covering application, non-application and missing evidence;
- an impact report against the conformance corpus;
- an updated coverage statement and changelog.

No pack version becomes stable solely because it has been merged. Stability requires an explicit maintainer release decision.
